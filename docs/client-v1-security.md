# Client API v1 安全与事务检查记录

本记录对应 `docs/client-v1.md` 和 `docs/client-v1.openapi.json` 描述的首版 `/client/v1`，基于 `HoshinoWork/SSPanel-UIM` 的 `feat/hysteria2-sspanel`，基线提交 `d6c6a98d`。这是一份代码审查与回归结果，不是渗透测试报告，也不承诺绝对安全。

## 审查范围与调用路径

- 入口：`app/routes.php` → `app/client-routes.php` → `src/Middleware/ClientApi.php` → `src/Controllers/Client/V1/*`。46 个 HTTP 操作在 OpenAPI 中逐一对应；公共操作限于配置、验证码、登录/注册/重置/刷新、受挑战保护的 MFA 网页及支付返回页。
- 全局错误处理：`src/Middleware/ErrorHandler.php` 对客户端路径先进入独立中间件，不先执行网页 Cookie 认证；未匹配路由和不允许的方法也返回 JSON。
- 身份与账户：`src/Services/Client/{Accounts,Sessions,Challenges,BrowserMfa,Limits,Input}.php`，复用面板用户和现有验证码/WebAuthn 密码学验证器，而非旧 API 空壳。
- 业务与资金：`src/Services/Client/{Idempotency,Commerce,Payments}.php` → `src/Services/Billing/{Transaction,Settlement}.php`；原网页下单、余额、礼品卡及易支付/当面付入口接入相同交易服务。支付结算基类、返佣及订单 Cron 同时检查。
- 数据与清理：迁移 `2026100600`、`Client/Maintenance.php` 及原 Cron。迁移仅新增六张客户端表；回滚仅移除这些新表，不删除原用户/账单/订单。
- 订阅：`UserController` 复用现有 `Subscribe::getContent/getUserNodes/getUniversalSubLink` 与订阅生成器。没有独立复制 VLESS/Hysteria2 转换规则；原订阅回归一起运行。

## 安全控制与修复

| 检查项 | 当前控制与证据 |
|---|---|
| 未认证访问 | 每一个受保护路由均拒绝缺失 Bearer；不接受网页 Cookie、管理员或节点令牌代替客户端会话 |
| 会话安全 | 随机不透明令牌，数据库只留散列；访问期限、会话总期限、撤销、封禁及密码摘要均校验；刷新一次性轮换，旧令牌重放撤销家族 |
| 并发刷新 | 用户 → 会话 → 刷新记录的加锁当前读，避免 REPEATABLE READ 的旧快照接受第二次消费；真实双进程测试验证一次成功、重放拒绝和家族撤销 |
| 越权与批量赋值 | 订单、账单、付款、会话按当前用户筛选；他人资源不允许读取或修改；PATCH 仅允许姓名，不接受余额、等级、UUID、封禁等自报字段 |
| OTP 与 MFA | 有效期、用途、邮箱/用户绑定、最多五次错误尝试、单次消费；错误计数提交，有效证明消费与业务写入同事务；MFA 不能用自报 approved 标志跳过 |
| WebAuthn/TOTP | WebAuthn 绑定用户、挑战、RP/来源与现有签名验证器；浏览器票据不能直接换会话；TOTP 检查格式并阻止窗口内重放 |
| 输入与错误 | HTTPS 默认要求；64 KiB JSON 对象上限、字段白名单、金额字符串校验；404/405/503 不返回堆栈/SQL/密钥；带 no-store、nosniff、no-referrer 和请求 ID |
| 验证码与限流 | 返回公开配置而非供应商私钥；实际提交服务端验证；IP/用户/流程限流，不信任任意客户端转发头；全局和路由中间件不重复计算同一次公共请求 |
| 敏感信息 | 资料/节点不下发服务端 custom_config、REALITY 私钥或商户密钥；日志不再保存原始礼品卡；支付失败仅记录异常类型，不输出 SDK 响应/付款凭据 |
| 回调校验 | 易支付签名/PID/成功状态，当面付 RSA2/app_id/成功状态；两者核对交易归属、网关和精确金额，拒绝嵌套数组参数与篡改通知 |
| 金额精度 | 报价、扣款、充值、余款、返佣采用 BCMath 和两位小数规则；日志旧接口的数值转换不用于确定实际资金变化 |

测试包含错误注入而非仅成功路径：账单或流水写入失败、证明后续业务失败、错误用途/归属、过期令牌、封禁、重放、回调金额/app_id/签名不匹配、网关连接超时，以及 debug 开启时未知客户端路径仍不泄漏网页错误。

## 原子性结论

前提：所有参与写入的原表与新表均为 **InnoDB**，位于同一数据库连接；没有并发绕开这些服务的外部余额/账单修改。迁移明确使用 InnoDB，但不会自动转换原表。

| 操作 | 同一数据库事务内的状态 | 并发/故障验证 |
|---|---|---|
| 下单 | 用户/商品/优惠码锁、资格与库存重查、订单、账单、次数、幂等结果 | 同键一单、最后库存不超售、优惠码全局额度、账单失败全回滚 |
| 余额支付 | 用户/账单锁、精确扣款、账单状态、流水、幂等结果 | 不重复扣款，流水失败余额与账单一起回滚 |
| 礼品卡 | 用户/卡锁、消费标记、余额、流水、幂等结果 | 两个用户竞争只有一个入账，流水失败不消费卡 |
| 支付通知 | 用户/账单/交易锁、到账状态、余款或晚到款、返佣 | 重复通知一次结算；并发返佣不丢余额；取消订单的晚到款不激活订单 |
| 充值激活 | 已支付账单检查、订单/用户锁、余额、订单 activated、流水 | 重复/并发激活一次入账，流水失败全回滚 |
| 验证后写入 | 锁定证明、消费、注册/改邮箱/密码重置/MFA 会话创建 | 有效证明后业务失败可重试，成功后不可重放，两个进程只执行一次业务 |
| 发起网关支付 | 在短事务内领取发起权，外部 HTTP 在事务外执行 | 同一付款只发起一次；超时不自动重发/换通道 |

用户行锁串行化其资金写入；库存、优惠码、礼品卡和证明还锁共享资源。财务服务要求调用时已处于事务，避免以后直接调用形成部分写入。幂等键绑定用户、操作和规范化请求，同键不同请求返回 409，资金幂等记录不按短期缓存清理。

锁定依赖中的 Illuminate 已处理死锁/锁超时重试；另补充 MariaDB 11.8 实测的 1020 快照冲突整笔回滚后重试。嵌套事务把冲突传播给外层，不对任意异常或无法确认的提交重试。并发用例同时验证 `innodb_snapshot_isolation=ON/OFF`，不是以 SQLite 代替 InnoDB 锁验证。

**不能宣称数据库与支付商户之间具有分布式原子性。** HTTP 超时可能已经在商户创建付款；领取后进程崩溃可能停在 creating。indeterminate、creating、未确认关单的过期尝试须人工查单，首版未实现供应商通用自动查单/关单。不得仅凭本地超时清除证据、自动重发或开放另一收费通道。套餐激活仍依赖原订单 Cron；回调入账不等于套餐立即生效。

## 尚未覆盖与风险边界

1. 尚未实测真实商户回款、真实公网异步通知及 Flutter Android/iOS/Windows/macOS 的验证码、Passkey 和支付 UI；供应商集成测试使用 Mock HTTP、测试 RSA 密钥和模拟签名通知。
2. 不等于全站安全审计：旧管理后台手动取消、标记已付、退款、其它支付网关发起支付及所有后台维护写入未获得本轮完整并发原子性认证。管理员操作须避免与自动结算并发；后续若要支持这种场景，应继续统一加锁和交易服务。
3. 邮件请求隐藏账号存在与否的响应内容，但发送耗时未恒定，不能保证抵抗时序枚举。限流依赖可信服务端 IP 配置，不能修复错误反向代理或被泄漏的面板密钥。
4. 会话撤销不是终止已经执行中的请求；重要写操作会复核用户状态，但不承诺全局即时取消。普通订阅 URL 是独立访问凭据，退出客户端不会撤销订阅链接。
5. 公告/文档是原始内容；原生端必须禁止任意脚本与不受控桥接。WebView 的限源、安全存储和日志脱敏须在 Flutter 实现中落实，服务端无法单独保证。
6. OpenAPI 描述路由、认证、请求及通用响应包装；`data` 仍有通用结构，并非所有响应都提供强类型 DTO。Flutter 应结合主文档与实测响应建模，不依赖自动生成覆盖所有业务字段。

## 启用前检查

- 备份数据库；确认原交易表使用 InnoDB。先部署迁移再启用 API；默认 `client_api_enabled=false`。
- 使用正式 HTTPS、正确的受信代理配置、独立强随机面板 key、debug=false；脱敏访问日志、请求体、支付动作及订阅链接。
- 验证邮箱发送、各验证码供应商正式域名、MFA 账户及四端浏览器桥的来源限制。
- 仅启用配置完备的易支付/支付宝当面付；执行授权小额支付、篡改/重复回调、超时与人工查单演练。不要用真实生产订单运行自动回归。
- 保持原订单 Cron 运行，确认已付款 → pending_activation → activated 的状态同步；观察余额、流水和返佣一致性。
- 发布前检查目标提交的远程 CI。异常回滚时先停客户端 API，并核对未完成付款；不要直接删除财务幂等/付款记录或在有未结交易时回滚新表。
